## The two cells that keep their stored value instead of a segment ratio

Rows 42 and 43. Both segments hold `null` rather than `0` in the DAC column, so no
numerator exists and no ratio can be computed. Blanking would have put a dash where
the stored value and ConEd's report both say 0%, which the project direction rules
out: the dashboard reproduces ConEd's report and the stored values are the
reference.

The rule is narrow by construction. It applies only to a total row that HAS a
segment, so a whole-table Grand Total still blanks when it cannot derive, which is
the CLCPA-88 behaviour behind the dashes on E1 and F9.

## A7 and the CLCPA-205 claim

CLCPA-205 item 1 asserted A7 was byte-identical. **That claim was about
`recomputeTotals`, and it remains true there.** This slice changes
`applyDerivedCols`, a different function, and A7 legitimately moves here: exactly
one cell, A7/2025 row 2, listed as row 43. A7/2024 is byte-identical in both.

The old code split A6/2025 row 31 and A7/2025 row 2 only by accident: A6's
whole-table DAC column has numeric data and A7/2025's does not, so one received a
wrong number (71.4%) and the other a dash. Treating them alike is the point.

## A note on the dashes in the labels

The label column contains 16 en dashes, inside program names such as "Clean Heat -
Commercial & Industrial Air Source Heat Pump". Those are reproduced VERBATIM from
`payload.json`, where they are data that must never be edited. The no-long-dash rule
governs text I author; quoted data is copied faithfully, because altering a program
name inside evidence would misrepresent the report it describes.
