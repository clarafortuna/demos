    DEFECT 2, and it is the one I did not see coming.

    applyOverrides replaces tables[].data and NOTHING ELSE. It does not
    touch charts, and it does not need to: A1's "% in DACs" is a DERIVED
    column, and the app recomputes derived columns at RENDER through the
    CLCPA-88 shared rule. So today the table DISPLAYS a computed 0.58
    even though the store holds null, and the payload's stored chart
    values hold 0.58 to match.

    The composer derives charts and KPI shares straight from the STORED
    table data, without recomputing the derived columns first. So every
    stripped derived cell propagates into the composed charts as null,
    where the app shows a number. A1 is in PERSIST_STRIP_TABLES along
    with 25 other tables, so this is not one chart: it is every chart
    and every KPI share that reads a derived column of a stripped table.

    THE FIX IS STRUCTURAL AND ALREADY EXISTS. The app has one shared
    derive engine, and the composer must run it over the composed table
    data before deriving anything from it -- exactly as the render path
    does. Not a new rule; the existing one, applied one step earlier.

    so of the four live divergences: TWO were the comparison baseline
    (tables, and the kpis coordinate that followed from it) and TWO are
    genuine composer defects. 2 of 5 on the fair comparison,
    against 1 of 5 on the unfair one.

=== 4. THE REAL DEFECT: current_year derives to a test year ===
  ok   the composer derives current_year = 2099
  ok   the payload publishes current_year = 2025

    MECHANISM. composePayloadFromRows sets current_year = years[0], the
    newest year carrying data. The org contains A1:2099, a row created
    during CLCPA-235 testing for a year the report does not cover, so
    the newest year with data is 2099 and the composer calls it current.

    WHY MY OFFLINE PROOF MISSED IT. gen_seed.js recomposed from the SEED
    FILES, which contain no 2099 row -- the payload has no such year, so
    the seed could not have one. The fixture was therefore structurally
    incapable of exposing this, and my "the fixture is what Dataverse
    holds" claim was true for 153 of 155 rows and false for the two that
    mattered.

    THE PRINCIPLE IT BREAKS. I derived current_year on the argument that
    storing it would be a second source of truth for a fact the rows
    already state. The 2099 row disproves that: the rows state which
    years HAVE DATA, which is not the same fact as which year the report
    COVERS. The first is data; the second is an editorial decision that
    cannot be derived from data at all. So current_year belongs in the
    meta row beside baseline_options, and deriving it was wrong on
    principle rather than merely unlucky.

    years[] is a different question and is NOT obviously wrong: the app
    already merges added years into meta.years through applyAddedYears,
    so a selector showing 2099 is what ships today. Left for Emely.
  ok   the derived year list leads with 2099: 2099, 2025, 2024, 2023

    CONSEQUENCE IF FLIPPED AS IT STANDS: the dashboard would open on
    2099 -- a test year with one table of data -- instead of 2025. Every
    KPI card and every chart would read from a year that has A1 and
    nothing else. That is not a subtle drift; it is the whole report
    landing on an empty year, and it is exactly what the shadow was
    built to catch before a flip rather than after.
