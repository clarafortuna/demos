# Geometry vintage change: hybrid to pure 2010

Generated by `Data/build_pure_geometry_dataset.py --vintage 2010 --artifact`.
Do not edit by hand: every number here is computed from the dataset it
describes, so the two cannot drift apart.

Distances are metres and areas are square metres, computed in
`NAD83 / New York Long Island (ftUS)` (EPSG:2263), not in degrees.

## What changes

The map swaps the 2020-with-2010-fallback hybrid for pure 2010 geometry.
The tract set does not move: the same 2333 tracts are drawn, none added, none
dropped. Every indicator value, KPI total, DAC count, population and account
sum is keyed on GEOID and the key set is unchanged, so **no number on the
dashboard moves**. Only shapes change, and 129 tracts gain a name.

## Display names

**Rule: a tract's display name resolves from the newest crosswalk that
contains its GEOID.** Not from the geometry vintage. The resolution source
is recorded per tract in the `neighborhoodSource` column, so the policy is
auditable in the data rather than inferred from it.

| resolved from | tracts |
|---|---:|
| 2010-table | 129 |
| 2020-table | 1987 |
| City_Town | 217 |

Sources, both NYC Department of City Planning:

- `2010-table` — NYC DCP, 2010 Census Tract to Neighborhood Tabulation Area Equivalency table, NYC Open Data 8ius-dhrr (2168 rows), 2010_Census_Tract_to_Neighborhood_Tabulation_Area_Equivalency_table_20260806.csv
- `2020-table` — NYC DCP, 2020 Census Tracts to 2020 NTAs and CDTAs Equivalency table (2327 rows)

### Why names do not follow the geometry vintage

Purity protects **data correctness**: indicator values must be paired to
their own vintage's geometry and key space, which is what the vintage guard
enforces. A display name joins on nothing. It labels a tract and groups the
neighbourhood filter, and no calculation reads it.

Naming each tract from its own vintage's table was measured before being
rejected. It would have relabelled 1,186 of the 1,987 already-named NYC
tracts, 618 of them DAC, which is 64.5% of the NYC DAC tracts. It would have
coarsened the vocabulary from 212 names to 192, because 2010 had 195 NTAs
against 2020's 262 and the newer revision split them. And it would have
turned 14 real names into `park-cemetery-etc-<borough>` placeholders,
including Central Park, Brooklyn Navy Yard, Pelham Bay Park and Randall's
Island, with not one case improving. That churn buys no correctness, and it
would fall hardest on exactly the population this dashboard exists to
highlight.

It would also repeat on every vintage toggle, burying the one thing a
vintage switch is meant to demonstrate. Under the newest-crosswalk rule the
demo invariant is stronger: **values stable, names stable, only shapes
change.**

## Reconciliation: this supersedes the earlier "0 of 2,235 identical"

Earlier records for this work state that **0 of the 2,235 GEOIDs present in
both vintage files have identical geometry**. That figure was carried into
the plan for this slice. It is superseded here, and should not be cited
again.

It came from comparing the two Census files by exact JSON equality, which
is not a test of shape. Two identical polygons compare unequal in those
files for two reasons that have nothing to do with geography. The files
start a ring at different vertices, so the same boundary is written in a
rotated order, and they carry different float representations of the same
coordinate, `-73.86670699999999` against `-73.866707`. Under exact
equality every tract therefore differs, which is what produced the 0, and
that number measured serialisation rather than geometry.

Measured properly, the noise has a ceiling. Compared against the 150 tracts
`map_payload.json` already draws from the 2010 file, where any difference
must be representational, the symmetric difference never exceeds
2.4e-10% of tract area. Across all tracts the band [1e-8%, 1e-6%] contains
no tract at all, so a threshold placed anywhere inside that gap separates
noise from geography without a judgement call, and moving it within the
gap changes no count. This document uses 1e-06%.

Restating the same file-to-file comparison under that threshold:

| comparison | identical | differing |
|---|---:|---:|
| exact JSON equality, as previously reported | 0 | 2,235 |
| symmetric difference in EPSG:2263 | **86** | 2,149 |

So 86 of the 2,235 shared GEOIDs genuinely did not change boundary between the
two vintages, not zero.

Two counts in this document are easy to collide, so to be explicit. The 86
above is a **file-to-file** count over the 2,235 GEOIDs the two Census files
share. The headline is a **payload-to-pure-2010** count over the 2,333 tracts
the map actually draws: 265 identical, of which 150 are tracts the payload
already drew from the 2010 file and 115 are shared-GEOID tracts whose
boundary did not move. The two differ because the populations differ, 2,235
against 2,333, and because the baselines differ: the payload is not the 2020
file, disagreeing with it on 967 tracts as the appendix below sets out. Both
numbers are correct for the comparison each one names.

## Appendix: map_payload.json does not match its own Census source

Found while validating the 2020 build, and recorded here because it is a
property of the data rather than a consequence of this change.

Of the 2183 tracts `map_payload.json` sourced from the 2020 Census file,
**967 carry a polygon that differs from the copy of that file in the repo**.
The payload is still clearly built from the 2020 file rather than the 2010
one. Matched against both files, 1,938 of the 2,183 sit closer to 2020, 162
closer to 2010 and 83 are indistinguishable, so this is not a wrong-vintage
problem: it is a disagreement between the payload and the current copy of
its own source.

| | |
|---|---|
| tracts compared | 2183 |
| differing above the noise floor | **967** (44%) |
| DAC among them | 419 |
| Non-DAC among them | 548 |

| metric | median | p90 | p99 | max |
|---|---:|---:|---:|---:|
| symmetric difference | 0.054% | 2.86% | 27.4% | 73.9% |

Most are tiny: 191 differ by more than 1%, 58 by more than 5%, 12 by more
than 25%. The 2010 file, by contrast, matches the payload's 150 fallback
tracts exactly, so pure 2010 geometry is unaffected by any of this.

**Hypothesis, not a finding.** The shape of the distribution suggests two
things at once: a small difference almost everywhere, which is what a
re-generalisation of the same source looks like, and a thin tail of
substantial reshapes concentrated on the waterfront, around the Financial
District, Battery Park and the Staten Island and Queens shorelines, where
the payload's polygons are usually the larger ones. Shoreline clipping
would explain the tail. None of this has been confirmed against the Census
release notes, and it should not be repeated as fact.

These datasets take the **Census file as authoritative**. A dataset that
claims Census provenance should carry Census polygons, and the payload's
variants are an instance of the payload not being reproducible from its own
inputs, which is the condition this project exists to retire.

One consequence to keep in view: because the baseline for the shape counts
above is the payload rather than a Census file, the 2068 changed shapes mix
two causes, the genuine 2010-against-2020 boundary difference and this
drift. They are reported together because together is what a viewer sees.
