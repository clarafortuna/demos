Where things stand today

The insight

Here's What the Migration Work Revealed

When we migrated from SharePoint to Dataverse, we had to maintain a separate document mapping every question in plain English to its database column name. That document exists because the question and its storage address were never the same thing. The database just treated them that way.

Three examples from the migration mapping — what the question says vs. where it's stored:

"Is the project likely to take place within 100 feet of wetlands or open waters?" → cf_nearwetlands
"Based on the asset's location, does the project take into account projections of extreme wind and icing conditions?" → cf_extremewindicing
"Does the project affect a Disadvantaged Community?" → cf_affectsdisadvcommunity

The proposed model does away with the shadow document. The question text, its code, and its metadata become actual data — a row you can edit, not a column name you have to release.

What Changes, Specifically

The app experience stays the same. For end users, nothing changes. The difference is what happens internally when the questionnaire needs to evolve.

Walk through it

What "Add a Question" Actually Looks Like

Say policy needs a new question: "Does this project include battery storage?" Here's what that looks like under the proposed model — from request to live question, without a schema change.

1

The policy team identifies a new question

Today, adding this question means opening a schema change request. Updating the app, the PDFs, possibly the strategy rules. A reasonable estimate: days of coordinated work for a yes/no question.

2

An admin adds one row to the question catalog

Code: BATTERY_STORAGE. Text, type, category, sort order. Done. No schema deploy. No release window needed.

3

The screening form reads the catalog at runtime

The new question appears in the right place, in the right category. Nobody touched the app.

4

Users answer the question normally

From the user's perspective, nothing is different. They answer the question. Behind the scenes, the app saves one new response row: the project, the question code BATTERY_STORAGE, and the answer.

5

If needed, a strategy rule follows the same pattern

If battery storage should trigger a specific strategy, an admin adds one mapping row: if BATTERY_STORAGE = Yes, activate this strategy. The strategy catalog doesn't change. Just a new rule pointing to the new question code.

Benefits

What Gets Better

The change is mostly invisible to end users. The value shows up for the teams who maintain and evolve the questionnaire over time.

Users & Stakeholders

  • Same journey — open a project, answer the screening, see the roadmap
  • Help text, question wording, and ordering are editable without a release
  • Question groupings and categories can evolve as the program does
  • Responses are traceable to a specific question, which helps with audits

Business & Policy Admins

  • Add or retire questions without filing a schema change request
  • One place to manage the full question library
  • Strategy rules live in a table you can review and edit directly
  • New questions can go into the new model before the full migration is done

Platform & Technology

  • The project table carries project data — full stop
  • Reporting on answers is a filter, not a 40-column join
  • Integrations and reports can reference question codes that don't change
  • One screen pattern handles all questions — far less custom formula logic
A few things to get right

What to Plan For

No honest proposal omits the trade-offs. These are the ones worth planning for.

Migration is real work

Converting the existing screening data is a one-time backfill job. It's scriptable and bounded, but it needs proper planning.

The admin experience matters

If the question catalog is difficult to maintain, it won't get maintained. A usable editing experience — even a basic one — isn't optional.

More rows means more attention to queries

A response table with many rows needs thoughtful indexing. Standard Dataverse design practice — not a blocker, but not free either.

Some complexity stays in code

Complex scoring logic will still need formulas or custom logic in places. The goal is to make that the exception, not the rule.

Path forward

Concept → Alignment → Phase 2

Nothing here blocks the work already underway. The intent is to start a conversation about direction — and decide together whether a pilot makes sense.
