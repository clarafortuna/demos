Section 00 — Audit Finding

Architecture Validation & Bias Corrections

Before building any component of this system, the architecture was subjected to a technical validation pass. Three critical biases were identified in the initial design and corrected. This section documents what was wrong, why, and what the correct approach is — as required by Document Control integrity standards.

1
Bias: "No additional licenses needed" — INCORRECT
Original (incorrect) claim
The initial architecture stated the agent could be built and used with "no additional licenses" beyond existing M365 accounts.
Correction
The HTTP with Azure AD connector in Power Automate is a Premium connector — it requires a separate Power Apps Premium or Power Automate Premium license. Additionally, every user who runs a flow that uses a Premium connector (SQL, PostgreSQL, SAP, etc.) also needs a Premium license. Clara Fortuna holds Power Platform Premium licenses which covers this. However, for client deployments connecting to external databases, each client user requires their own Premium license — this is a per-client cost that must be communicated upfront. Source ↗
2
Bias: Direct HTML → Dataverse connection — INSECURE
Original (incorrect) design
The initial architecture connected the GitHub Pages HTML directly to the Dataverse API using an Azure AD token obtained in the browser.
Correction
While technically possible to call Dataverse directly from a browser with a Bearer Token, this exposes the organization URI and all API calls to browser developer tools. More critically, any server-side operations requiring application permissions (not just delegated user permissions) cannot be done safely from a browser. The correct architecture routes all API calls through Power Automate as server-side middleware. The browser only holds the user's identity token — all privileged operations execute server-side. Source ↗
3
Bias: Client secrets in frontend code — CRITICAL VULNERABILITY
Original (incorrect) approach
Early design iterations included storing client secrets in the JavaScript code to authenticate against Power Automate or Dataverse.
Correction
Client secrets embedded in frontend code are visible to anyone who views the page source. This is a well-documented security vulnerability. The corrected architecture uses: (1) MSAL.js PKCE flow — no client secret required in the browser; (2) Azure Key Vault for all secrets accessed by Power Automate server-side; (3) Delegated permissions only in the browser — the user's token represents their own identity, not an application identity with elevated privileges. Source ↗
Section 01

Executive Summary

The Clara AI Lab Agent is the technological centerpiece of Clara Fortuna's newest strategic initiative — the Clara AI Lab — announced to the company in April 2026.

Business Context — Why This Exists

The utility sector is undergoing rapid technological transformation. Through conversations with industry leaders and ongoing discussions across the utility space, one thing has become clear: utilities need a space where they can explore, test, and innovate rapidly — without immediately running into the barriers that come with internal IT structures.

The Clara AI Lab was created precisely for this purpose: a space where utility clients can experiment with emerging technologies, evaluate solutions, and move ideas forward in a setting built for innovation. The lab is designed to help clients think bigger, test sooner, and develop practical recommendations that can later be brought back into their organizations in a structured way.

To support this vision, Clara Fortuna formally separated the functions of Innovation and Development in April 2026. The Innovation department — led by Euris as Director of Innovation — now focuses exclusively on the Clara AI Lab, emerging technology evaluation, and AI-driven solutions for utility clients. Development (Randdy, Emely, with Manny as interim supervisor pending Director selection) handles solution delivery and platform support.

What the Agent Does

The Clara AI Lab Agent is a browser-based, conversational AI interface that allows citizen developers — users with no coding knowledge — to design, build, publish, and manage Microsoft Power Platform model-driven applications entirely through conversation. No access to the Power Apps maker portal is required. No technical training is needed.

The agent guides users through a structured workflow: describe what you need in natural language → the agent designs the data model → confirm the design → publish to the Dev environment → get approvals → promote to QA → promote to Production. The entire lifecycle is managed from a single interface hosted on GitHub Pages.

Section 04

Azure AD Authentication with MSAL.js

The agent uses OAuth 2.0 Authorization Code Flow with PKCE — the recommended flow for browser-based SPAs. Implemented through @azure/msal-browser, the official Microsoft library.

Verified: MSAL.js (@azure/msal-browser) implements OAuth 2.0 Authorization Code Flow with PKCE for browser-based applications without backend servers. OpenID-compliant. Replaces deprecated Implicit Flow. MSAL Browser Docs ↗

Authentication Flow

1
User opens agent URL
Browser loads static HTML from GitHub Pages. MSAL.js initializes and checks for cached token in session memory.
2
Redirect to Microsoft login
MSAL.js calls loginRedirect(). User enters corporate credentials: user@clarafortuna.com. This is the same login page as Office 365, Teams, and Outlook — no new credentials required.
3
Azure AD issues Bearer Token (JWT)
Token valid for 60 minutes. MSAL.js stores it in session memory only — never in localStorage or cookies. Token disappears when tab is closed.
4
Silent renewal via acquireTokenSilent()
Before any API call, MSAL.js renews the token silently if needed. User never sees a second login prompt.

Section 05

Security Model

🔐
Layer 1 — Identity
Azure AD authentication. Only clarafortuna.com tenant users. Enforced by Microsoft Entra ID — not by the agent itself.
🛡️
Layer 2 — Transport
Power Automate HTTP trigger requires Azure AD Bearer Token. "Any user in my tenant" setting. Anonymous calls are rejected with HTTP 401.
🗝️
Layer 3 — Secrets
All connector credentials in Azure Key Vault. Retrieved by Power Automate at runtime only. Never written in code or browser.
Client Secret Risk: Storing a client secret in frontend JS exposes it to anyone viewing page source. The architecture avoids this entirely via PKCE (no secret needed) and server-side Power Automate execution. Source ↗
Power Automate HTTP Trigger Security (Verified): Three authentication modes available: (1) Anyone — SAS token, no auth; (2) Any user in my tenant — valid Azure AD Bearer Token required (this architecture uses this); (3) Specific users in my tenant — whitelist by email. Source ↗
Section 06

Agent Publication Workflow — 6 Steps

When a user is ready to publish a designed app to Dev, the agent guides them through 6 structured steps. No technical knowledge required. No environment is touched until Step 6 explicit confirmation.

1
Model Confirmation
Agent presents complete summary: tables, relationships, forms, modules, visual design. Three options: Confirm (proceed), Request changes (chat continues, model updates, returns here), or Cancel (see Section 06.A). Nothing is applied to any environment.
2
Name and Description
Four fields: (1) Display name — what users see; (2) Unique name — Dataverse internal ID, prefix cf_ enforced by the Clara Fortuna publisher; (3) Description — optional; (4) Version tag — defaults to DEV-v1.0. Agent validates uniqueness against target environment in real time. Agent suggests 3 names based on the model designed in the session.
3
Target Environment Selection
Agent queries Power Platform API to retrieve environments available to the authenticated user. Each shown as a card with status, URL, region, and app count. Production is always locked for citizen developers — only System Administrators can publish to Production. Selecting QA shows a warning to validate in Dev first.
4
Security Roles Assignment
Agent queries Dataverse for all security roles in target environment. Without at least one role, the published app is invisible to all users — including the publisher. Basic User is always recommended as minimum. System Administrator shows a caution badge. User can proceed without roles but sees a warning.
Verified: "Users assigned to the associated security roles can see and use your model-driven apps in Dataverse." An app without roles is published but invisible. MS Learn ↗
5
Data Source Confirmation
Three options: (1) Dataverse — agent lists session tables, verifies existence in target environment; (2) External database (SQL/PostgreSQL/MySQL/Oracle/SAP) — user provides credentials, agent tests connection live through Power Automate — mandatory before proceeding; (3) Power Automate Flow — select existing flows in tenant that connect to external systems.
6
Final Confirmation Summary + Publish
Full summary of all 5 steps with edit links. Agent runs automated pre-publish checks (connection, tables, roles, token). User must check an explicit confirmation checkbox before Publish button activates. Progress bar shows each internal API step in real time. On success — see Section 06.B for confirmation screen details.
Section 06.A — Audit Correction (Finding #3)

Cancellation and Correction Flow

At any point during the 6-step workflow, the user can stop. The agent preserves all progress and offers 4 recovery options. No environment changes are ever made before Step 6 confirmation.

State Preservation

When the user pauses or cancels, the agent maintains the complete state of all completed steps in session memory:

StepWhat is preserved
Step 1Full model — tables, relationships, forms, modules, visual design
Step 2App name, unique name, description, version tag
Step 3Selected environment and its connection details
Step 4Selected security roles list
Step 5Data source type, connection details, tables confirmed

4 Recovery Options

✏️
1. Correct a specific step
Return to any step directly. All other steps remain saved. Most common option — user noticed an error in one field only.
💬
2. Modify the model in chat
Describe the change in natural language. Agent updates the model and automatically returns to Step 6 with updated summary.
💾
3. Save session for later
Agent saves complete state with a unique session ID (e.g. AILab-Session-20260417-EU-001). User can resume in another session by referencing the ID.
🗑️
4. Discard and start over
Requires double confirmation. Agent explicitly confirms Dev environment was NOT affected since nothing was published. Model and all step data are cleared.
Key Principle: Discarding a session has zero impact on any Dataverse environment. The agent never writes to Dataverse before Step 6 explicit publish confirmation. The "discard" warning is for user peace of mind — not because data was at risk.

Section 07

Internal API Flow — What Happens When the User Publishes

One button click → ~12 seconds → done. Internally: 6 sequential API calls through Power Automate. Each depends on the result of the previous one.

#StepAPI CallTimeOn Failure
1Token validationMSAL acquireTokenSilent()~1sRe-authenticate user
2Create AppModulePOST /api/data/v9.2/appmodules~2sAbort — nothing created
3Register tables (parallel)GET + POST EntityDefinitions~3sRollback: DELETE AppModule
4Add forms/views/web resourcesPOST appmodulecomponents (type 60, 26, 61)~2sRollback: DELETE AppModule
5Assign security rolesPOST appmoduleroles_association/$ref~1sNotify — retry this step only
6Publish app (PublishXml)POST /api/data/v9.2/PublishXml~2sRollback: DELETE AppModule
Rollback Principle: If any step after AppModule creation fails, the AppModule is deleted via DELETE /api/data/v9.0/appmodules({id}). The environment returns to its exact pre-publish state. Never a partial publication.

Section 11

QA → Production Promotion Flow

Production promotion is significantly stricter than Dev→QA. Errors in Production affect real utility clients with real operations. The process reflects that consequence.

No Friday Deployments. Production deployments are restricted to Tuesday and Thursday, 8:00–10:00 AM EST. Fridays are prohibited because weekend support coverage is reduced — limiting the ability to execute a rollback if needed. Mondays are planning days. This is a standard enterprise DevOps practice followed by organizations including Microsoft itself. Source ↗

Change Window Justification

Why Tuesday and Thursday, 8–10 AM EST specifically:

  • Monday excluded: Teams are in planning mode — reduced availability to respond to incidents
  • Friday prohibited: If a critical issue emerges Friday afternoon, the on-call team has reduced capacity over the weekend to execute a rollback or hotfix
  • 8–10 AM EST: Low user activity window before business peak. If the deploy fails, there is time to roll back before the majority of users are affected
  • 2-hour window: Sufficient for the deployment pipeline (~12s) and initial monitoring period, while leaving time for rollback decision if needed

Section 14 — Audit Correction (Finding #12)

Power Platform Connectors — Data Source Options

The agent supports any data source a utility client uses. Three integration patterns were evaluated. Power Platform Connectors (Option 2) was selected as the primary approach.

Three Integration Options Evaluated

🔗
Option 1 — Virtual Tables
Connect SQL/PostgreSQL/MySQL directly to Dataverse as virtual tables. Data stays in client's database. Not selected — requires more complex setup and limited connector support vs. Option 2.
⚡
Option 2 — Power Platform Connectors ✓ Selected
Agent calls Power Automate flows that use Premium Connectors. Server-side, secure, 1,000+ data sources, covered by existing Clara Fortuna Premium licenses.
🌐
Option 3 — Direct REST API
For client systems with exposed REST APIs. No connector needed. Available as fallback when no native connector exists for a specific system.
Licensing Verified (March 2026): Premium connectors — including SQL Server, Azure SQL, Dataverse (outside M365), Salesforce, ServiceNow, SAP, Oracle — require a Power Apps Premium or Power Automate Premium license per user. Clara Fortuna holds Power Platform Premium. Client deployments: each client user running a premium connector flow requires their own Premium license. Source ↗
