FieldValue
TypeText
Primary PurposeBase Power Apps URL for deep links in flow emails
CriticalityHigh

Stores the environment-specific Unified CSR Portal application URL. Flows append navigation query parameters to direct users to specific screens.

Used In

Functional Behavior

cf_ev_app_url
+ "&nav=PendingRequest" or "?nav=EmployeeInteractionsLog"
= deep link URL in outbound email
🟡 Warning: Flow files contain explicit fallback URLs as hardcoded parameter defaults.

Impact if Misconfigured

  • Missing: Broken or absent portal links in notification emails.
  • Wrong environment value: Recipients land in wrong tenant/environment.
  • Invalid format: Malformed links and navigation failures.

Power Automate Flows

UCP_Approval_Notification

Trigger: PowerApps V2 | Complexity: Medium

Trigger payload: Name, DateRange, RequestType, CSRFunction, DayPortion, Email, v_ActivePhase, IssuedByMail.

Logic Summary

  1. Resolve employee manager via Office 365 Users.
  2. Send approval email via Office 365 Outlook.
  3. Include manager and issuer in CC; BCC from environment variable.

UCP_Approval_Denial_Notification

Trigger: PowerApps V2 | Complexity: Medium

  1. Triggered by app with outcome status.
  2. Manager lookup.
  3. Branch by OutcomeStatus (Approved vs else) and send matching email.

UCP_Approval_Request

Trigger: PowerApps V2 | Complexity: Medium

  1. Triggered by app on request submission.
  2. Manager lookup for target user.
  3. Sends pending approval notification including app link using cf_ev_app_url.

UCP_Approval_RequestV2

Same functional intent as UCP_Approval_Request with revised message body and environment value defaults.

UCP_Cancel_Notification

  1. Triggered by app cancellation action.
  2. Manager lookup.
  3. Sends cancellation notice to CSR with manager+issuer CC and env BCC.

UCP_Denial_Notification

  1. Triggered by app denial action.
  2. Manager lookup.
  3. Sends denial notice.

UCP_Notification

  1. Triggered by app for approved notifications.
  2. Manager lookup.
  3. Sends approval notice.

UCP_Notification_Interactions

Switch-based multi-scenario interaction notifier (create/update/delete/late slip/compass). Payload includes 15+ contextual fields.

TRIGGER: PowerApps event payload
  → Switch on EventType
     → INT_SUPERVISOR_CREATED: notify employee/supervisor
     → LS_SUPERVISOR_CREATED: late slip issued + app deep link
     → INT_SUPERVISOR_UPDATED / LS_SUPERVISOR_UPDATED
     → LS_CSR_RESPONDED / INT_DELETED / LS_EXCUSED_UPDATED
     → CPS_SUPERVISOR_CREATED: compass certificate email
OUTPUT: contextual email notifications
🔴 Risk: Very large embedded HTML strings and many branches significantly increase maintenance risk and test surface area.

UCP_Daily_Late_Slip_Missing_CSR_Comment_EST

Trigger: Recurrence daily at 07:00 EST

Compliance notification for late slips missing CSR comments. Filters cf_employeeinteractionlogs for empty comment fields retaining only Late Slip type records.

🟡 Warning: Contains a BCC Compose action with literal email addresses in addition to environment variable usage.

Canvas App — Control-Level Formula Extraction

Screen: App (OnStart)

Business Rules Summary

  • Access to key areas is determined by whether the signed-in user is registered as Admin, Supervisor, Developer, or CSR in Dataverse tables.
  • Users who do not meet role or phase conditions are routed to UnavailableScreen.
  • The employee function and approval type determine whether leave requests follow automatic or management-approved workflows.
  • Navigation parameters support deep-linking users into specific contexts (pending approvals, interaction logs).
  • Environment mode is read from Dataverse with a fallback to the variable default value.

Screen: LeaveRequestScr

Business Rules Summary

  • CSRs can only submit leave requests if their profile data is complete; incomplete profiles show an error notification and block submission.
  • Leave type determines whether the request requires manager approval or is auto-approved based on cf_approvalmethod.
  • Date handling references cf_ClosedDay records — non-working dates configured centrally are excluded.
  • Only records in Approved or Pending status are shown in the request gallery.
  • Submitting a leave request triggers UCP_Approval_RequestV2 for manager-facing notification.
  • Canceling a leave request triggers UCP_Cancel_Notification and patches the LeaveRequestDetail status in Dataverse.
  • Calendar navigation (prev/next month) adjusts _firstDayOfMonth, _firstDayInView, _lastDayOfMonth global variables.
  • Users with cross-screen dependency on gblUserEmail (set in App.OnStart) — if app starts on this screen directly, role checks may fail.

Screen: SupervisorPortal

Business Rules Summary

  • Supervisors can approve, deny, or cancel leave requests for their direct reports.
  • Approvals and denials trigger UCP_Approval_Denial_Notification with the outcome status.
  • Cancellations trigger UCP_Cancel_Notification and patch LeaveRequestDetail records directly.
  • Leave request dates reference closed day records — non-working dates are excluded from calculations.
  • Function/Section dropdowns filter the employee gallery to show only relevant team members.
  • The "Select All" toggle (varSelectAll) enables bulk approval/denial across multiple request rows.
  • Only Pending/Approved status records are surfaced for supervisor decision-making.

Screen: AdminPortal

Business Rules Summary

  • Admins can submit leave requests on behalf of any CSR in any function/section.
  • Approval and denial actions trigger UCP_Approval_Denial_Notification flow.
  • Cancellation triggers UCP_Cancel_Notification and patches LeaveRequestDetail status.
  • Leave type configuration (notification flag, send time) controls whether automatic notifications fire.
  • Process phase management (Phase 1/2/3) gates certain admin actions via cf_ProcessPhaseFlags.
  • Allotment tracking shows taken/remaining hours per function per date — driven by cf_FunctionAllotment.
  • Closed day, Leave Type, Allotment, CSR Profile, and Supervisor Profile records are all manageable from this screen.
  • Supervisor profile form auto-populates email, number, and full name from the selected supervisor dropdown.

Screen: EmployeeInteractionsLog

Business Rules Summary

  • Access and available actions differ based on whether the user is a CSR, Supervisor, or Admin — controlled by gblIsCSR, gblIsSupervisor, gblIsAdmin.
  • Creating or updating interaction records triggers UCP_Notification_Interactions with the appropriate event type.
  • Late slip records require Slip Type and Minutes Late fields; Compass records require Compass Type.
  • CSRs can respond to late slips via a comment field; the response triggers a notification event.
  • Supervisors can mark late slips as excused, which updates the cf_excused flag and triggers an update notification.
  • Interaction records can be soft-deleted (deletedby/deletedon fields populated) rather than physically removed.
  • The interaction type tab list filters the gallery between General Interactions, Late Slips, and Compass entries.
🟡 Multiple delegation risks in OnVisible, Container3/Visible, grl_MyEmployees/Items. 🟡 Four cross-screen global variable dependencies.

Screen: AccessControl

Business Rules Summary

  • Only users with admin-level access can manage roles and user assignments on this screen.
  • Roles are assigned to users through the cf_accesscontrol table with an active flag.
  • User search is powered by Office 365 Users connector with potential delegation limits on large directories.
  • Role changes trigger a Patch operation that updates both old and new role assignments.
  • Delete confirmation dialogs gate all destructive operations before execution.
🟡 Delegation risk in UserBrowseGallery/Items (O365 Users query).
