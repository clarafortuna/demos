01 · System flow

Six stages, one feedback loop

From trigger to audit, each stage maps to a native Microsoft component.

Stages 01 + 02

Triggers and agent

Two events invoke the agent. The agent itself runs in Copilot Studio with five read-only tools and a strict system instruction that bounds its behavior.

Stage 01 · Triggers

Scheduled and event triggers

Two triggers invoke the agent: a recurring daily timer for routine monitoring, and a webhook from the Power Platform Admin API when capacity exceeds a configured threshold. Both shape the same payload before invoking the agent so downstream logic stays uniform.

Stage 02 · Agent

Copilot Studio agent

Hosted in Microsoft Copilot Studio with five tool connectors and a strict system instruction. The agent reads capacity metrics and Dataverse data, but only writes through the action layer downstream of human approval. Versioned, testable, and governable through standard ALM.

5 read-only tool connectors

Stages 03 + 04

Analysis and approval

The agent produces a structured proposal in one pass. The proposal renders as a Microsoft Teams adaptive card with per-line approval. Nothing executes until the steward responds.

Stage 03 · Analysis

Structured proposal

The agent produces three artifacts in a single pass: a risk summary with projected breach timing, a ranked list of cleanup candidates by impact in GB, and recommendations that pair each candidate with an action type. The output is structured JSON consumed by downstream stages.

Stage 04 · Approval

Microsoft Teams adaptive card

The proposal renders as an adaptive card in the data steward channel. Each recommendation can be approved, modified, or rejected individually. No downstream action runs until the approval payload returns through Power Automate. This is the consent boundary.

Stages 05 + 06

Actions and audit

Each approved recommendation maps to one of four bounded action types. Every proposal, approval, and execution is logged. The agent reads its own history on the next run.

Stage 05 · Actions

Four bounded action types

Each approved recommendation maps to one of four actions: archive to Azure, bulk delete, file offload, or audit retention reduction. Power Automate flows execute each action with hard blast radius limits enforced before any change reaches Dataverse.

02 · Implementation

Native Microsoft components only

Every component in the architecture maps to an existing Microsoft service. The agent runs in Copilot Studio, orchestration runs in Power Automate, and all data services are first-party. No custom infrastructure is required.

03 · Approval workflow

The human in the loop

The adaptive card is the boundary between agent autonomy and human judgment. Every recommendation is reviewable. The card payload is the artifact compliance teams will request when auditing the agent.

The card supports three response patterns: approve all selected items, customize the selection before approving, or reject all and provide feedback that the agent reads on its next run.

Recommendations are sorted by impact in GB and color-coded by action type. Items that were skipped in previous runs are flagged so the steward sees the pattern without reading the full audit log.

Design principle
The agent earns autonomy through approved history. Trust is granted incrementally based on the audit log, not assumed at deployment time.

04 · Considerations

Decisions before deployment

Three load-bearing decisions to make before production deployment. Each one shapes how much autonomy the agent is granted on day one and how that autonomy expands over time.

G.01

Approval granularity

Per-recommendation approval is safer but creates Teams card fatigue. Batch approval is faster but riskier. Recommended path: per-recommendation for the first quarter, then graduate to batch for action types that have a clean history in the audit log.

G.02

Action limits

Hard-code blast radius ceilings that the agent cannot override. Cap bulk deletes at 10,000 records per action and archives at 50 GB per pass. A misjudged recommendation should be wrong, never catastrophic.

G.03

Environment scope

One agent per environment is simpler to govern and easier to permission. Tenant-wide scope is more powerful but needs careful Service Principal design. Start scoped, then expand once the audit log shows clean runs.

Closing

What to build first

A pragmatic implementation order. Each step is independently valuable and unblocks the next.

1
Read-only telemetry flow

A Power Automate flow that reads the Admin API daily and writes capacity to a Dataverse table. No agent yet, just the visibility layer.

2
Copilot Studio agent skeleton

Stand up the agent with the capacity reader tool. Have it produce risk summaries on demand. Validate output structure before adding action paths.

3
Teams adaptive card as a one-way notification

Post proposals to Teams without action buttons. Operators read and act manually. Builds steward trust and surfaces card-design issues early.

4
One action path, end to end

Wire archive-to-Synapse as the first executable action. Choose archive over delete to keep the first agent action reversible.
